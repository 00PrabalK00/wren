# W4_RayViTRayConditionedVisualRepresentation — RayViT: Ray-Conditioned Visual Representations for Viewpoint-Robust Imitation Learning (2026, arXiv id not in text)
Setup: DINOv3 ViT-S (21.6M, fully fine-tuned) + 3.85M gated cross-attn ray module; Plücker ray map (from calibrated K, R, t) → ray-conditioned CLS token + ray positional embeddings; aux cosine loss aligning CLS tokens of different views (gripper view as anchor, layer 10, weight 0.01). Policy: score-based diffusion, xLSTM decoder, chunk 10, DDIM 4 steps, CLIP language. Sim: RoboCasa 16 tasks multi-task, 50 human demos/task, 2 static cams + gripper cam, 3 seeds, 50 eps/task; variant = static cams randomly rotated (azimuth/elevation) and shifted in distance. Real: Franka Panda, 2 ZED Mini external + RealSense D405 wrist, 256×256, joint-position actions; 4 tasks, 50 demos (100 for insertion), 20 rollouts/task; variant = right camera moved to a substantially different pose. Train on single RTX 5090 in 7 h.
Claim: Injecting camera geometry via ray maps into a pretrained ViT (plus cross-view consistency) makes policies robust to camera moves without multi-view data augmentation or depth.
Evidence: RoboCasa avg SR (default → variant): RGB DINOv3 42.5 → 24.0 (drop 18.5); RayViT-cls 43.2 → 37.0 (6.2); RayViT 39.8 → 37.3 (2.5); Adapt3R (3D) 41.7 → 28.5 (13.2); PMP-xyz point map 42.1 → 20.8 (21.3); PMP (RGB+points) 35.6 → 17.0. Real (avg completed stages, default → variant): RGB 2.44 → 0.91; RayViT-cls 2.26 → 1.70; RayViT 2.81 → 2.69. Per task RGB variant: Drawer 2.95→0.45, Cup Stack 3.40→1.05; RayViT Cup Stack 3.50→3.35.
Ablations: no cosine loss: RayViT-cls 38.4/30.6, RayViT 39.5/35.6 (default/variant) → cosine loss adds ~+4 default, +2–6 variant; cosine loss on plain RGB gives no stable gain (figure only). Deeper-layer placement of cosine loss better (figure only). From scratch (no pretrain): RGB 29.2/10.0 vs RayViT 32.1/29.2 → pretrained DINOv3 +13 default for RGB. EUPE backbone: RGB 44.1/18.9, RayViT 44.3/33.3.
Failure/limitations: authors — ViT only, relies on multi-view anchor for consistency loss. My read: requires extrinsic calibration at test time — if the camera is bumped, you must re-measure pose (they assume known new extrinsics); real tasks have fixed object layouts; 20 rollouts. Default performance slightly lower with ray PE on DINOv3.
Conflicts: Point-cloud/point-map (3D) inputs were NOT more viewpoint-robust (PMP-xyz drop 21.3, worse than RGB) — contradicts the common belief that 3D inputs automatically give viewpoint invariance; consistent with Adapt3R's own claim that 3D-in-camera-frame still depends on extrinsics. Agrees with TAP (this wave): plain RGB policies collapse under camera shifts.
Relevance: Directly addresses our "slightly moved camera" failure. Our RealSense scene cam can be calibrated (AprilTag) cheaply; wrist cam extrinsics come from forward kinematics — so ray maps are available for both. DINOv3 ViT-S (22M) fine-tuned end-to-end fits 8 GB. But if the shifted camera pose is unknown at deployment, the benefit requires re-calibration; the cross-view consistency (wrist anchor) may still help.
Decision impact:
 - Q14 robustness (camera shift): supports camera-geometry conditioning (ray maps) + cross-view consistency: drop 18.5 → 2.5 pts sim, real 0.91 → 2.69 stages — confidence M (sim 3 seeds + real 20 rollouts)
 - Q04 3D/depth: weakens point-map/point-cloud input as a viewpoint-robustness fix (PMP-xyz drop 21.3 vs RGB 18.5) — confidence M
 - Q03 vision encoder: pretrained DINOv3 ViT-S fine-tuned >> scratch (42.5 vs 29.2 default) — confidence M
 - Q11 cameras: wrist camera as anchor view for consistency loss; 2 static + wrist setup — confidence L
 - Q09 aux objectives: cross-view cosine consistency helps only with geometry-aware tokens — confidence L-M
